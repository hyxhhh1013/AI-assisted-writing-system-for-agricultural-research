# grainscript-feature — 产品设计：意图 → 原子方案 → 规格

## 产品原则

**系统要精简、能力要原子化。** 新功能不是默认正确答案；默认答案是：用已有工作台路径、Passport 阶段、入口或字段解决，或做一个最小原子能力挂进现有链路。

业务说的往往是**症状或方案**（「加个按钮」「加个 Tab」「再开一个审查」），产品要还原成**意图**（谁、在卡什么、成功长什么样），再判定值不值得做、做成什么样。

不要写长 PRD。不确定的业务规则标「待确认」，不要猜死。不要伪造调研数据。

## 与现有规范的分工

| 文档 | 管什么 |
|------|--------|
| **本 skill** | 功能诉求的产品拆解：真伪需求、原子方案、改哪里、怎么验收 |
| [`docs/VIBECODING.md`](../../../docs/VIBECODING.md) + [`AGENTS.md`](../../../AGENTS.md) | 范围钉死之后怎么写代码、怎么验证、怎么同步文档 |
| [`docs/MASTER_PLAN.md`](../../../docs/MASTER_PLAN.md) | 产品主轴与防乱铁律：新功能必须回答挂在工作台哪条路径、是否写入 Passport；禁止再开第三条可视化流水线 |

本 skill **内嵌轻量对抗**（意图与真伪需求）。诉求若是「要不要做整条新产品线」，先对照 MASTER_PLAN 的优先级（安全 > 文档一致 > 已排期 Wave > 新功能），再回本 skill 落规格。

## 何时用 / 不用

| 用 | 不用 |
|----|------|
| 新功能、改流程、加入口、扩权限或 Passport 边界 | 范围已钉死的修 bug / 改文案 / 调样式 |
| 「我们要个…」「先出方案」 | 明确说「直接按我说的做、别分析」——仍可在内心过一遍真伪判定，但输出从简 |
| 人控写作与 Agent 两条入口、或写作 / 审查 / 查重 / 知识库 / 图表交叉 | 已有清晰 checklist，只差写代码 |

## 内部思考（不原样输出）

按序过一遍；拿不准时放慢，清晰时加速。

```
听诉求 → 还原意图 → 判真伪 → 定处置类型 → 原子方案 → 挂接现网 → 写规格
```

### 1. 还原意图（表象 ≠ 需求）

把「要加 X」翻译成：

- **谁**在什么情境卡住了？
- 他们真正想完成的 **Job** 是什么？（不是想要哪个控件）
- 现在靠什么凑合？成本/风险是什么？
- 做成之后，**哪一条可观测结果**算成功？

追问上限：**1 个**关键 blocker（选择题优先）。能从 `docs/domain/` 与代码推断的不要问。

### 2. 真需求 vs 伪需求

| 信号 | 更像真需求 | 更像伪需求 |
|------|------------|------------|
| 问题形态 | 有重复发生的卡点、差错、引用或阶段违规 | 「别人家有」「感觉应该有」「顺便也做」 |
| 方案绑定 | 能接受多种实现 | 死盯某一种 UI/新页面，说不清 Job |
| 现网关系 | 现有流程明显缺口或错误 | 现有能力已覆盖，只是不会用 / 入口难找 |
| 代价 | 不做会持续产生错误稿、越界引用或阶段跳步 | 不做几乎无事，做了增加认知负担 |
| 可验证 | 能写出验收行为 | 只能写出「有个页面看着更全」 |

**伪需求常见变形**（倾向拒绝或改写，而不是照做）：

- **方案冒充需求**：点名「加导出 / 加看板 / 再加一个审查维度」但说不清因此少了哪类差错
- **流程债外包给功能**：规则、口径、权限没想清，却要求新页面承接
- **堆叠式安心感**：多一个状态、多一个开关「以防万一」
- **角色或模式越权**：为少点两下而绕过 Passport 阶段铁律，或让人控与 Agent 各写一套
- **复制外部形状**：照搬通用聊天或多一个独立写作站，未映射到项目章节、文献池和引用约束

判定为伪需求 → 输出里写清「不建议做 / 建议改成什么」，**不要**继续编完整实现清单假装要做。

### 3. 处置类型（决定后面写多深）

| 类型 | 定义 | 产品动作 |
|------|------|----------|
| **A · 立刻做** | 真需求；缺口清晰；可落在**已有原子**上（扩字段、补校验、补入口、对齐人控与 Agent）；横切面小 | 短规格 → 按 VIBECODING 实现 |
| **B · 设计后做** | 真需求；但碰 Passport 阶段、引用编号语义、新 Agent 工具、新数据对象、多入口或流式事件 | 先定原子边界与挂接点，再规格；大改等一句确认 |
| **C · 改写后再做** | 诉求方向偏了，但底下有真 Job | 提出改写后的原子方案，请确认 Job 是否说对 |
| **D · 不做 / 延后** | 伪需求，或真需求但优先级低于精简 | 说明原因 + 若坚持的最小代价方案（可选） |

类型边界与例子见 [references/requirement-types.md](references/requirement-types.md)。

### 4. 原子化设计（默认减法）

优先序：

1. **不建新表面** — 能否在现有工作台路径、Tab、列表、详情或弹窗完成？
2. **扩展已有原子** — 章节、引用、审查、查重、检索、图表、Agent 工具是否已有同类可复用？
3. **一个 Job 一个原子** — 禁止「万能中心」「再一个写作工作台」式堆砌
4. **规则优于新流程** — 能改 Passport、权限或 prompt 规则，就不要加状态机分叉
5. **新模块是最后手段** — 必须新原子时，写清它挂进哪条现网链路、是否写入 Passport、与哪条主轴互斥

每个推荐方案用一句话说清：**做什么、为什么、代价、若不做会怎样**。若有更省的替代路径，必须写出来（即使提出方点名了另一方案）。

### 5. 挂接现网（类型 A/B 必做）

按需 Read，不要全库扫。

| 文档 | 用途 |
|------|------|
| [`docs/DOMAIN_INDEX.md`](../../../docs/DOMAIN_INDEX.md) | 功能 → 代码入口 |
| [`docs/domain/`](../../../docs/domain/) 对应篇 | 写作、RAG、图表、审查查重、Agent 的不变量 |
| [`docs/MASTER_PLAN.md`](../../../docs/MASTER_PLAN.md) | 主轴与「挂在哪条路径、是否写入 Passport」 |
| [`AGENTS.md`](../../../AGENTS.md) S2、S5 | 业务不变量与完成检查清单 |

横切勾选（不涉及也要标）：Passport 阶段 · 引用是否落在检索范围内 · 项目保存是否仍为增量更新 · 人控与 Agent 入口是否一致 · 写作或 Agent 流式事件 · 知识库与检索 · 图表注册表 · `docs/` 是否随功能一起改。

## 输出格式（≤1 页；按处置类型裁剪）

思考过程不展示。只给决策要用的结论。

```markdown
## <一句话功能名>

### 意图
- 提出的说法：…
- 还原的 Job：谁 / 情境 / 要完成什么 / 成功长什么样
- 现网缺口或误用：…

### 判定
- 真伪：真需求 | 伪需求 | 部分真（说明）
- 类型：A 立刻做 | B 设计后做 | C 改写 | D 不做/延后
- 一句话理由：…

### 方案（A/B/C 才写）
- 推荐（原子级）：…（优先复用：…）
- 不做清单：…
- 备选（若有）：更省或更险的一条 + 适用条件

### 挂接与改动（A/B；C 仅在改写已被认可后）
- 横切：Passport / 引用 / 增量保存 / 人控与 Agent / 流式事件 / 知识库 / 图表 / 文档
- 挂接点：工作台哪条路径；是否写入 Passport

### 验收（A/B）
- [ ] 主路径…
- [ ] 失败、越界引用或阶段未满足…

### 待确认（≤2，可选）
- …
```

**类型 D**：意图 + 判定即可，可附「若坚持，最小代价是…」。
**类型 C**：把改写后的 Job 说清楚，等确认后再展开改动表。

---

## 输出后动作

- **A**：规格明确 → 直接实现（`docs/VIBECODING.md` 顺序 + `AGENTS.md` 铁律）。
- **B / C**：有 blocker 或新原子 → 等确认后再写代码。
- **D**：停在产品结论；不假装开工。
- 新业务规则写回对应 `docs/domain/` 或 `docs/MASTER_PLAN.md`；与代码同一批改动，不另开「以后补文档」。

---

## 反模式

- 把点名的 UI 原样翻译成开发任务
- 用新页面或新 Tab 掩盖未想清的规则
- 真伪未判就写满前后端改动表
- 长 PRD、展示推导过程
- 漏人控/Agent 双入口、漏引用约束、发明与 Passport 冲突的阶段
- 为一次汇报或一次性材料做永久功能
