# 需求类型速查（按需打开）

SKILL 正文已含判定逻辑。本页给禾书耕文的边界例子。

## A · 立刻做（扩原子 / 补缺口）

- 已有弹窗或缺字段、缺校验，规则在 domain 文档已写明
- 人控写作与 Agent 对同一能力行为不一致（一边能写进章节，另一边不能）
- 流式事件类型在契约里有，但某条路径没发出或没消费
- 文案或空态让人以为没有功能——优先改发现性，不新建页面

## B · 设计后做（新原子或横切深）

- 新 Passport 阶段，或改动「配置确认 / 大纲批准」这类阶段铁律
- 新 Agent 工具，或改变引用编号、越界剥离的语义
- 新业务对象（新表、新主实体）
- 写作、审查、查重、知识库之间的责任重新划分
- 「中心 / 总览 / 再一个工作台」类聚合诉求——先拆成若干原子 Job

## C · 改写

- 「加个查重按钮」→ 真实 Job 可能是现有查重入口难找 → 先补发现性
- 「再加一个写作模式」→ 可能只是某条工作台路径没挂上，不应再开主轴
- 「加个导出」→ 先问导出之后哪一步少出错；常常是现有稿面缺字段
- 「给 Agent 也开这个」→ 先划清与人控入口的同一行为，再谈新表面

## D · 不做 / 延后

- 仅「看着更专业」的装饰性页面
- 可用文案或入口位置解决的「找不到功能」
- 为极低频个案开永久分叉
- 与 Passport、引用约束或增量保存冲突，提出方不愿改规则，只想系统迁就
- 为一次阶段汇报或一次性材料做进产品的永久能力

## 原子化检查（方案过门）

1. 能否用一句话描述该原子的**单一职责**？不能 → 再拆。
2. 删除该原子后，哪条主链路断了？说不清 → 可能不该存在。
3. 是否引入新阶段或新状态？是 → 写明与 Passport 现有阶段的互斥与迁移，否则打回。
4. 是否新表面（页 / Tab / 大弹窗）？是 → 先证明现有工作台路径放不下，并回答是否写入 Passport。
